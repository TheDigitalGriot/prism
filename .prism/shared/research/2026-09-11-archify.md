## Mechanism

### The pipeline, end to end

```
natural language
   |   (performed by the CLAUDE MODEL, guided by archify/SKILL.md — no code)
   v
typed JSON IR  ------------  archify/schemas/{architecture,workflow,sequence,dataflow,lifecycle}.schema.json
   |
   |- validate  ------------  bin/archify.mjs (validate) -> renderers/shared/validator.mjs:38
   |                          emits {code,severity,message,subject,evidence,supportedFixes}
   |                          -> model repairs the JSON -> loop (SKILL.md:22-35)
   v
per-type renderer  --------  renderers/<type>/render-<type>.mjs  (resolved at bin/archify.mjs:54-64)
   |                          layout + SVG string built here
   v
writeDiagram  -------------  renderers/shared/cli.mjs:53-70 -> single standalone .html
   |                          (SVG string injected into archify/assets/template.html)
   v
browser viewer runtime  ---  viewer/*.js, inlined into the template by scripts/generate-viewer.mjs

```

### The diagnostic contract — the repair loop's real payload

`renderers/shared/validator.mjs:38-86` `validateSchema(diagramType, data)`. On failure it maps every ajv error into:

```js
{ code: `schema/${error.keyword}`, severity: 'error', message,
  subject: {diagramType, path, identity},
  evidence: {keyword, expected, ...error.params},
  supportedFixes: [...] }
```

- `validator.mjs:6-19` `annotatedPath()` — walks the JSON pointer and resolves **the nearest enclosing element's `id` or `label`**, so `/nodes/3/label` is reported as `/nodes/3 (id/label: "router") /label`. The header comment at `validator.mjs:4-5` states the reason outright: *"reads much better ... for the LLM fixing the JSON."* **The diagnostic format is designed for a model reader.** This is the single highest-value idea in the repo.
- `validator.mjs:56-68` `supportedFixes` — a keyword-to-imperative-sentence table: `additionalProperties` -> "remove unsupported property X"; `required` -> "add required property Y"; `enum` -> "choose one of [...]"; `pattern`, `minimum`, `maxItems`, `minLength`, etc. The validator hands back *actions*, not complaints.
- The same envelope is used by the CLI itself: `bin/archify.mjs:43-52` `rejectCliArgument()` attaches `{code, subject, evidence, supportedFixes}` to argument errors, and `bin/archify.mjs:56-61` is a worked instance.
- The stopping rule is authored in prose, not code — `SKILL.md:35`: *"Continue focused correction while the objective error count reaches a new minimum. If two consecutive rounds do not improve that best count, stop and report the unresolved diagnostics truthfully."*

## Layout

**Layout is mostly AUTHORED (it lives in the IR), not solved.** There are two distinct regimes.

### Regime A — architecture / sequence / dataflow / lifecycle: fixed cell math, no auto-layout

`archify/renderers/architecture/grid.mjs:1` — the file own first line reads:
`/** Grid placement for architecture IR (#8). Not auto-layout — fixed cell math only. */`

- `grid.mjs:3-11` `DEFAULT_GRID = {mode:'grid', origin:[40,80], cols:4, gapX:30, gapY:40, cellW:130, cellH:64}`
- `grid.mjs:13-17` `gridLayout(arch)` — returns `{...DEFAULT_GRID, ...arch.layout}`, or `null` when the author omitted `layout` (free placement).
- `grid.mjs:19-31` `resolveComponentPos(component, grid)` — **`pos` wins outright** (`:20-22`); otherwise `[origin.x + col*(cellW+gapX), origin.y + row*(cellH+gapY)]` (`:27-30`). No graph algorithm, no ranking, no force simulation.
- `grid.mjs:33-62` `validateGridPlacement()` — records problems for missing placement (`:44-47`), negative row/col (`:48-51`), col beyond cols (`:52-54`), and **duplicate cell occupancy** (`:55-58`).

So for four of the five types, **the LLM is the layout engine** and the code is a coordinate resolver plus an overlap checker.

The heavy lifting in `renderers/shared/geometry.mjs` (1,423 lines) is **edge routing and collision diagnosis**, not node placement — visible in the import list at `renderers/architecture/render-architecture.mjs:13-43`: `automaticPortSpread`, `automaticPortRhythmBridge`, `defaultFromSide`/`defaultToSide`, `chosenSide`, `routeHonorsEndpointSides`, `normalizeRoutePoints`, `polylinePath`, `roundedPath`, `labelPoint`, plus the diagnosis family `cleanEndpointSideProblems`, `cleanFlowProblems`, `cleanCrossingProblems`, `cleanAmbiguousCorridorProblems`, `cleanBorderRunProblems`, `cleanRouteRhythmProblems`, `cleanLabelRouteClearanceProblems`, `suggestLabelObstacleFix`, `suggestComponentSeparation`.

`render-architecture.mjs:64-80` holds the tuning constants (`defaultW:120, defaultH:60, margin:40, boundaryPad:30, boundaryExtraBottom:20, boundaryLabelBaseline:18, legendH:28`), with a comment at `:68-69` naming the 30/50 boundary-padding rule as a prior hand-arithmetic bug (CHANGELOG v2.2.1).

### Raster and vector export: browser-side, at 4x

All of this lives in `viewer/export.js` (1,269 lines), inlined into every artifact. **Nothing rasterises in Node.**

- `viewer/export.js:1-12` — header comment states the strategy: Raster exports are always rendered at 4x source resolution for maximum sharpness; the serialized SVG width/height are set to viewBox * 4 so the browser rasterizes the vectors at that resolution natively, and drawImage then draws at the image natural size (no upscaling, no blur). JPEG/WebP paint the current theme background explicitly since those formats have no alpha channel.
- `:14` **`var RASTER_SCALE = 4;`** — the 4x claim is REAL.
- `:15-20` `MOTION_DURATION = 6000`, `MOTION_FPS = 30`, `SHARE_CARD_WIDTH = 1200`, `SHARE_CARD_HEIGHT = 630`, `SHARE_CARD_PADDING = 36`, `SHARE_CARD_HEADER = 112`.
- `:226-251` `serializeSvg(scale, opts)` — clones the live SVG and sets width to `vb.width * scale` and height to `vb.height * scale` (`:250-251`). Comment at `:248-249`: this is the key to sharp rasters, do NOT scale later. Returns dimensions at `:383-384`.
- `:407` `var MAX_CANVAS_PIXELS = 16 * 1024 * 1024;` with the reason at `:402-406` — older iOS Safari silently produces a blank canvas above roughly 16 Mpx.
- `:409-414` `pickSafeScale(vbW, vbH)` — the largest `s` in `{4,3,2,1}` such that `vbW*s*vbH*s <= MAX_CANVAS_PIXELS`. **So 4x is the default, not a guarantee.**
- `:416-461` `rasterize(format)` — `pickSafeScale` (`:423`), `serializeSvg(scale)` (`:424`), an SVG Blob (`:425`), Image load, a canvas sized to the serialized dimensions (`:433-434`), `ctx.drawImage(img, 0, 0)` at natural size (`:441`), then `canvas.toBlob(mime, quality)` (`:446-449`). MIME selected at `:443-444` (jpeg, webp, else png); quality is `undefined` for PNG and `0.95` otherwise (`:445`). JPEG gets an explicit background fill first (`:436-439`) because it has no alpha.
- `:664-665` the WebM motion path deliberately drops to `scale = Math.min(1, 1280 / vb.width)` — **motion capture is NOT 4x.** Frame compositing at `:759`.
- `:593-596` the Share Card is a separate 1200x630 PNG path.

## Lift notes for prism-viz-engine layer 01

Scope reminder: the ruling is **ADOPT + GRAFT** — the pattern is lifted into a native Prism generator at `apps/prism-viz-engine/src/layers/01-generate/`, emitting **JSON Canvas (Obsidian spec v1.0)** through the existing `apps/prism-viz-engine/src/core/json-canvas.ts`, feeding an xyflow canvas at layer 02. archify is not run as-is.

**The boundary being grafted is exactly `NL -> typed JSON IR`.** Everything downstream of that boundary in archify (SVG builders, the HTML template, the viewer runtime, the raster exporters) is irrelevant to us, because our sink is JSON Canvas rather than HTML.

1. **Graft the IR-first contract, not the renderer.** What makes archify work is that the model authors a closed-world, `additionalProperties: false`, enum-heavy JSON document, and a validator hands back imperative repairs. Our layer 01 is: prompt contract -> typed spec -> validator -> JSON Canvas.

2. **Our IR can be JSON Canvas plus a semantic sidecar, because the archify IR is already positional.** `architecture.schema.json:117-127` puts `pos: [x,y]` and `size: [w,h]` on every component — the same model as JSON Canvas `{x, y, width, height}`. The clean mapping:
   - archify `components[]` / `nodes[]` / `participants[]` / `states[]` -> JSON Canvas `nodes[]`. The normalisation table to copy is `renderers/shared/cli.mjs:72-78`.
   - archify `connections[]` / `edges[]` / `messages[]` / `flows[]` / `transitions[]` -> JSON Canvas `edges[]`. Table at `cli.mjs:80-86`.
   - archify `fromSide` / `toSide` (`common.schema.json:22-24`, values left/right/top/bottom) -> JSON Canvas `fromSide` / `toSide`. **The vocabularies are identical; this maps verbatim.**
   - archify `componentType` (7 values, `common.schema.json:39-41`) -> JSON Canvas exposes only 6 preset colour slots. This needs a deliberate decision: collapse two categories, use a hex colour, or carry the semantic type in a Prism extension field and let layer 02 colour it.
   - archify `boundaries[]` (`architecture.schema.json:131-148`, shaped `{kind, label, wraps, pad}`) -> JSON Canvas `group` nodes. Note archify groups by **membership** (`wraps`) while JSON Canvas groups by **geometry**, so the lift must compute a bounding box; `renderers/shared/layout-report.mjs` `boundaryBox` and the padding constants at `render-architecture.mjs:70-71` are the reference.
   - archify `cards[]` (`common.schema.json:98-113`) -> either JSON Canvas `text` nodes, or dropped to layer 02 chrome.
   - archify `components[].sources[]` (`architecture.schema.json:99-114`, shaped `{path, line, end_line, label}`) -> a natural fit for a Prism extension carrying code evidence. This is how archify pins a node to real code, alongside `meta.repository.revision`, a 40-hex commit at `:35`.

3. **The workflow layout receipt is the closest existing artifact to JSON Canvas.** `workflow-compiler.mjs:4286-4312` already emits `nodes: [{id, lane, col, x, y, width, height}]` and `edges: [{id, from, to, points}]`. If we want a solved layout rather than an authored one, that receipt shape is the target output of our solver, and `--layout-json` (`bin/archify.mjs:21`, `render-workflow.mjs:19-23`) is the precedent for exposing layout as data separate from pixels.

4. **Copy the diagnostic contract verbatim in shape.** `{code, severity, message, subject, evidence, supportedFixes}` (`validator.mjs:44-79`), together with the `annotatedPath()` id/label resolution (`validator.mjs:6-19`) and the keyword-to-fix table (`validator.mjs:56-68`). This is what makes a model repair loop converge, and `validator.mjs:4-5` states plainly that the format exists for the LLM reading it. Pair it with the authored stopping rule at `SKILL.md:35` — keep correcting while the objective error count reaches a new minimum; after two consecutive rounds with no improvement, stop and report truthfully.

5. **Decide the layout regime explicitly, and record the decision.** The archify answer for 4 of 5 types is that the model places the nodes (`grid.mjs:1`); for workflow it is that the model assigns lane and rank while the solver assigns X only (`workflow-compiler.mjs:159-338`). Since layer 02 is xyflow, either regime yields valid JSON Canvas. The constraint-relaxation solver is small — roughly 30 lines of actual solve at `:306-338` — and is portable without a dagre or ELK dependency. Its provenance-set idea (`:311`, `:323-333`, with contributor strings minted at `:199-203`, `:250-255`, `:270`, `:279`) is worth keeping: every column coordinate can explain which constraint produced it.

6. **Keep a single type router.** `bin/archify.mjs:13`, `cli.mjs:50`, and `preview.mjs:18` triplicate the same five-element list; one exported constant is the obvious native form. The type-to-collection maps at `cli.mjs:72-86` are the mechanism that lets one codepath serve every type — that is the piece worth lifting.

7. **The prompt layer is data, not code.** `recipes/scenarios.mjs:2-26` shows the record shape — `{id, type, presentation, signals, prompt}` — a scenario recommender with weighted bilingual keyword scoring, surfaced through `archify guide`. The Prism equivalent belongs in the same shape: a data file the skill reads, never a prompt builder in code.

8. **Bounded loops with named budgets and named failure codes.** `maxLayoutIterations = 3` (`workflow-compiler.mjs:163`), `MAX_READABLE_LAYOUT_FEEDBACK_ROUNDS` (`:4344`, `:4389`), guided views `maxItems: 5` (`common.schema.json:81`), `sources` `maxItems: 3` (`architecture.schema.json:102`), the trace-step clamp of 12 (`cli.mjs:174`), and the authored ceiling of 12 primary nodes (`SKILL.md:21`). Every loop that can fail has a diagnostic code for exhaustion — `workflow/solver-budget-exhausted` at `:4324`.
