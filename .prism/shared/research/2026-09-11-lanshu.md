# Lanshu Animated Architecture Diagram — the spec → `.excalidraw` emitter

## LOUD CORRECTIONS TO PRIOR RESEARCH — read before anything else

Prior research was carried as UNVERIFIED. Three of its claims stand; **the most
load-bearing one is wrong**, and it is wrong in the exact place our architecture
depends on.

### WRONG — "JSON spec → editable .excalidraw" implies a spec that describes a diagram

**There is no node/edge graph anywhere in this repo.** The spec is **not** a diagram
description. It is a **content-slot fill-in form for one single hardcoded picture.**

The entire diagram — every box, every arrow, every coordinate — is literal numeric
constants in the body of one function, `render_static()`, `scripts/render_animated_diagram.py:456-554`.
The spec supplies only *strings and icon keys* poured into fixed slots:

- `scripts/render_animated_diagram.py:486` — the Archive Core panel is `draw_rect(..., 53, 317, 1104, 320, ...)`. Hardcoded.
- `scripts/render_animated_diagram.py:489-491` — the three core cards sit at x=`95`, `472`, `850`, y=`366`. Hardcoded.
- `scripts/render_animated_diagram.py:492-494` — the arrows between them are hardcoded point lists: `[(355, 411), (472, 411)]`, `[(732, 411), (850, 411)]`, `[(982, 456), (982, 481), (768, 481), (768, 508)]`.
- `scripts/render_animated_diagram.py:478` — the four input slots are `zip([423, 532, 640, 748], inputs[:4])`. Four. Literally four x-values.

There is **no `nodes` array, no `edges` array, no `id`, no `from`/`to`, no
`x`/`y`/`width`/`height` in the spec at all.** Verified by reading
`assets/default-spec.json:1-138` in full and `references/spec-format.md:1-89` in full.

`references/spec-format.md:17-18` states this in the source's own words:
> "The renderer uses **fixed art-directed positions**"

and `README.md:55`:
> "Uses a **fixed high-quality layout**"

and `README.md:252-263` ("Design Notes"), which frames it as deliberate:
> "This project intentionally keeps the visual system narrow... That constraint keeps
> outputs consistent and polished across different architecture topics."

**So: Lanshu does NOT do the move our architecture depends on.** The premise that it
is "the ONLY tool in the cluster that already does the exact move" needs correcting —
it serializes *a picture it already knew how to draw* into `.excalidraw`. It does not
serialize *a structured graph* into a canvas format. There is no layout pass, because
there is nothing to lay out.

What it **does** give us, genuinely, is the second half of the seam: a clean, small,
readable **`.excalidraw` element emitter** (the `Excal` class, 105 lines) that is
worth studying as a writer. That is the liftable part.

### WRONG — "grouping/nesting" is expressed in the spec

Grouping is expressed **only** as spec *key names* (`left_panel`, `center_panel`,
`right_panel`, `core.cards`) that route content to a pre-drawn frame. In the emitted
`.excalidraw`, `groupIds` is `[]` on **every single element** — observed, not inferred:
159/159 elements have `groupIds == []` (emitted at `scripts/render_animated_diagram.py:201`).
Nesting is visual coincidence (a rectangle drawn around other rectangles), never structural.

### CONFIRMED — "pure-Python, no APIs"

That is the whole dependency list (`requirements.txt:1`). Observed check across all

## Mechanism (file:line for every claim)

Single script, 773 lines: `scripts/render_animated_diagram.py`. There is no package, no
module split, no classes beyond one.

### Entry point
- `main()` — `scripts/render_animated_diagram.py:752-769`. `argparse` with four flags:
  `--spec` (required, path to spec JSON, :754), `--outdir` (required, :755),
  `--basename` (default `animated-diagram`, :756), `--verify` (:757), `--check` (:758).
- Spec is loaded with a bare `json.loads(Path(args.spec).read_text())` at
  `scripts/render_animated_diagram.py:761`. **No schema validation of any kind** — no
  jsonschema, no key checking, no type checking. Missing keys are absorbed by `.get()`
  defaults deep inside the draw calls.
- `write_outputs(spec, outdir, basename)` at :762 does all the work.
- `--check` failure exits nonzero at :768-769.

### The one-pass dual-emit design (the interesting architectural move)

The core pattern: **every draw call writes to two sinks simultaneously** — a PIL
`ImageDraw` surface *and* an `Excal` element list — in a single pass. There is no
intermediate scene graph, and no second traversal.

This is visible in the `draw_*` helper signatures, which all take `(ex, draw, ...)`:
- `draw_rect()` — `scripts/render_animated_diagram.py:300-302`: line 301 appends the Excalidraw element, line 302 draws the pixels.
- `draw_ellipse()` — :305-307 (same shape: :306 element, :307 pixels)
- `draw_line()` — :310-326 (:311 element, :312-326 pixels incl. manual dash stepping)
- `draw_diamond()` — :329-334 (:330 element, :331-334 pixels)
- `draw_text()` — :283-297 (:289 element, :297 pixels)

Consequence: **the `.excalidraw` and the `.png` cannot diverge in content**, but also
**the `.excalidraw` can never be richer than what the raster pass needed** — no bindings,
no groups, no containers, because PIL has no concept of them (see "What NOT to copy").

### `write_outputs()` — `scripts/render_animated_diagram.py:652-664`
1. `:653` mkdir
2. `:654` `ex, static = render_static(spec)` — the dual-emit pass
3. `:655` `final = premium_finish(static)` — glow / grain / vignette post-process
4. `:659` save PNG
5. `:660` build frames via list comprehension over `animate_frame(final, i, frames)`
6. `:661-662` save GIF (`duration = int(1000 / fps)`, `loop=0`, `optimize=False`)
7. `:663` `ex.write(excalidraw_path)` — the `.excalidraw` is written **last, from state accumulated during step 2**
8. `:664` returns `{"png","gif","excalidraw","elements"}`

Note the ordering fact: **the `.excalidraw` is a by-product of the raster pass**, not the
source of it. Reverse of our architecture, where the canvas file is the wire and the
render comes after.

### Verification helpers (worth lifting conceptually)
- `frame_diff_report(gif_path)` — :667-685. Re-opens the written GIF, seeks 5 sampled
  frames (`[0, n//4, n//2, 3n//4, n-1]`, :669), `ImageChops.difference` between
  consecutive picks (:677), counts non-black pixels (:683). This is a **self-check that
  the animation actually moved** — the tool proves its own output rather than asserting it.
- `check_outputs(result, spec)` — :688-749. 12 named contract checks, each
  `{"name", "ok", "expected", "actual"}`: gif exists/width/height/frames/fps (:706-710),
  `gif_has_motion` from the diff report (:715-721), `excalidraw_exists`,
  `excalidraw_unique_ids`, `excalidraw_text_font_family == 5`, `excalidraw_files_empty`
  (:730-734), png exists/width/height (:742-746). Returns `ok = all(...)` at :749.

## The `.excalidraw` serializer

### The `Excal` class — `scripts/render_animated_diagram.py:176-280`

This is the liftable artifact. 105 lines. It is a **pure element-list accumulator with a
JSON writer** — no layout, no measurement, no dependency on PIL.

**`__init__`** (:177-182): holds `width`, `height`, `elements: list`, `count: int`, and a
`random.Random(2069769416930414980)` seeded with a **fixed constant** (:182). The same
constant appears again at :575 for the film-grain RNG. This is the determinism mechanism:
Excalidraw requires per-element `seed` and `versionNonce` integers, and a fixed RNG makes
successive runs byte-identical.

**`base()`** (:184-215) — the single element factory. Every element type routes through it.
The emitted element dict, verbatim from :186-213:

```python
{
  "id": f"{prefix}-{self.count:04d}",       # :188  e.g. "rect-0012"
  "type": kind,                              # :189
  "x": round(x, 2), "y": round(y, 2),        # :190-191
  "width": round(w, 2), "height": round(h, 2),  # :192-193
  "angle": 0,                                # :194
  "strokeColor": stroke,                     # :195
  "backgroundColor": fill or "transparent",  # :196
  "fillStyle": "solid",                      # :197
  "strokeWidth": stroke_width,               # :198
  "strokeStyle": stroke_style,               # :199
  "roughness": 1,                            # :200  <-- see "hand-drawn"
  "opacity": 100,                            # :200
  "groupIds": [],                            # :201
  "frameId": None,                           # :202
  "index": f"a{self.count:04d}",             # :203  fractional-index z-order
  "roundness": roundness,                    # :204
  "seed": self.rng.randint(1, 2147483646),   # :205
  "version": 1,                              # :206
  "versionNonce": self.rng.randint(...),     # :207
  "isDeleted": False,                        # :208
  "boundElements": None,                     # :209  <-- see "edges"
  "updated": UPDATED,                        # :210  frozen constant 1782475200000 (:17)
  "link": None,                              # :211
  "locked": False,                           # :212
}
```

`UPDATED = 1782475200000` (:17) is a **frozen epoch-ms timestamp baked into every
element** — another determinism device (a real `time.time()` would make output
non-reproducible).

**ID scheme** (:188): `f"{prefix}-{self.count:04d}"` where `count` is a monotonic counter
incremented at :187. Prefixes come from the typed wrappers: `"rect"` (:218), `"ellipse"`
(:221), `"diamond"` (:224), `"text"` (:227), `"arrow"`/`"line"` (:244). IDs are
**positional and meaningless** — `rect-0012` says nothing about what it is.

**Z-order** (:203): `"index": f"a{self.count:04d}"`. Excalidraw's fractional-index
ordering; here simply insertion order, so z-order == the order `render_static()` happens
to draw things.

**Typed wrappers**:
- `rect()` :217-218 → `roundness = {"type": 3}`
- `ellipse()` :220-221 → `roundness = None`
- `diamond()` :223-224 → `roundness = {"type": 2}`
- `text()` :226-241 — calls `base()` then `.update()` with the text-specific fields
  (:228-240): `text`, `fontSize`, `fontFamily: 5` (**hardcoded**, :234),
  `textAlign`, `verticalAlign: "top"`, `baseline: int(round(size * 1.25))` (:236),
  `containerId: None` (:237), `originalText` (:238), `lineHeight: 1.25` (:239).
- `line()` :243-265 — `kind = "arrow" if arrow else "line"` (:244)

**`write()`** :267-280 — the file envelope:
```python
{
  "type": "excalidraw", "version": 2,                 # :270-271
  "source": "https://excalidraw.com",                 # :271
  "elements": self.elements,                          # :272
  "appState": { "viewBackgroundColor": THEME["bg"],   # :274
                "gridSize": 20,                       # :275
                "currentItemFontFamily": 5 },         # :276
  "files": {},                                        # :278
}
```
Written with `json.dumps(..., ensure_ascii=False, indent=2)`, UTF-8 (:280).
`ensure_ascii=False` is why the CJK signature `@岚叔` survives readably.

### How are coordinates assigned?

**Neither of the two options in the question.** There is no layout pass, and the spec
carries no positions. **Coordinates are literals in the source code.** Every `draw_*`
call in `render_static()` (:456-554) passes numeric constants:

- `:464` title accent bar: `[(29, 31), (29, 78)]`
- `:466` highlight capsule: `600, 27, 392, 72`
- `:470` outer frame: `18, 117, 1174, 994`
- `:476` input box: `389, 138, 430, 101`
- `:486` core panel: `53, 317, 1104, 320`
- `:497` decision diamond: `706, 508, 120, 120`
- `:515`/`:522`/`:543` the three bottom panels: `39,735,281,344` / `333,734,522,346` / `904,735,258,344`
- `:528` center card x-positions: `zip([346, 486, 626, 766], layer_cards)`
- `:550` the five decorative `+` crosshairs: `[(375,292),(704,293),(1048,292),(315,707),(868,707)]`

The only "computed" positions are trivial offsets from a passed-in origin inside the card
helpers — e.g. `core_card()` :435-439 draws at `x`, `x+14`, `x+110`, `x+92`; `mini_card()`
:442-446 at `x+10`, `x+78`. The origins themselves are still literals from the caller.

Text is the **one** place anything is measured: `fit_text()` (:157-173) descends font
sizes from `size` down to `emergency_min` (:164), and for each size tries wrapped and
unwrapped variants (:166) until `text_size()` fits `(max_width, max_height)` (:168).
`EMERGENCY_MIN_TEXT_SIZE = 6` (:144). Wrapping is CJK-aware: `has_cjk()` (:84-85) checks
U+3400–U+9FFF, and `wrap_line()` (:112-134) splits on characters for CJK (:115-116) vs
spaces for Latin. This is **text fitting inside a fixed box**, not layout.

`SCALE = 2` (:16) and `c(v)` (:46-47) are a 2x supersample for the raster pass only;
the image is downsampled with LANCZOS at :554. The `.excalidraw` coordinates are
**unscaled** — `ex.rect()` receives raw `x`, the `draw.rounded_rectangle()` receives
`scaled_box(x,...)`. See `draw_rect()` :301 vs :302.

### How are edges bound to nodes in the output?

**They are not.** This is explicit, not an omission:

- `scripts/render_animated_diagram.py:263-264`:
  ```python
  element["startBinding"] = None
  element["endBinding"] = None
  ```
- `scripts/render_animated_diagram.py:209`: `"boundElements": None` on every element.

Confirmed by observation: 14 arrows emitted, **0** with a binding; 159 elements, **0**
with `boundElements`.

An arrow is stored as a **free-floating polyline**: `line()` computes the bounding box
from the point list (:245-248), sets the element `x`/`y` to `(min_x, min_y)`, and stores
points **relative to that origin** at :262:
```python
element["points"] = [[round(x - min_x, 2), round(y - min_y, 2)] for x, y in points]
```
Arrowheads in the PNG are drawn separately by `arrow_head()` (:359-365) using
`math.atan2` — that is raster-only; the `.excalidraw` relies on Excalidraw's own
`type: "arrow"` rendering.

Likewise **text is never bound to its container**: `containerId: None` (:237), observed 0/53
set. A label inside a box is just a text element that happens to sit at the same coords.

**Consequence for a downstream consumer:** open the file in Excalidraw and drag a box —
the arrows stay put and the label stays put. There is no graph in the output, only ink.

## Animation

### Verdict: animation is a **POST-PROCESS over rendered raster frames.** It is NOT a property of the spec, and it is NOT in the `.excalidraw`.

The spec's only animation-related fields are `canvas.frames` and `canvas.fps`
(`assets/default-spec.json:5-6`) — two scalars. Nothing in the spec says what moves,
where it moves, or along which path.

### `animate_frame(base, idx, total)` — `scripts/render_animated_diagram.py:613-649`

Takes the **finished flat PNG** and composites an RGBA overlay onto a copy (:614-616, :648).

**The motion paths are 11 hardcoded point-lists with hardcoded colours and phase offsets**,
`scripts/render_animated_diagram.py:618-630`:
```python
paths = [
  ([(605, 239), (605, 316)], THEME["green"], 0.00),
  ([(355, 411), (472, 411)], THEME["cyan"], 0.10),
  ([(732, 411), (850, 411)], THEME["cyan"], 0.24),
  ([(982, 456), (982, 481), (768, 481), (768, 508)], THEME["core_stroke"], 0.38),
  ([(826, 568), (1022, 568)], THEME["green"], 0.54),
  ([(707, 568), (510, 568), (222, 568), (222, 456)], THEME["purple"], 0.66),
  ([(156, 637), (156, 736)], THEME["green"], 0.18),
  ([(205, 736), (205, 637)], THEME["green"], 0.58),
  ([(458, 890), (486, 890), (598, 890), (626, 890), (738, 890), (766, 890)], THEME["purple"], 0.32),
  ([(855, 890), (904, 890)], THEME["white"], 0.46),
  ([(1036, 735), (1036, 691), (766, 691), (766, 628)], THEME["amber"], 0.72),
]
```
These are **duplicated by hand** from the static arrow coordinates — e.g. path 2
`[(355,411),(472,411)]` is a copy of the `draw_line` at :492; path 4 is a copy of :494;
path 6 is a copy of :505. Two independent hardcoded lists that must be kept in sync
manually (see "What NOT to copy").

**The moving dot**: `progress = idx / total` (:617). For each path, three trailing dots at
offsets `[(0, 1.0), (-0.035, 0.72), (-0.07, 0.44)]` (:632) — a comet tail. Position from
`point_at_fraction(points, progress + offset + trail)` (:633), which wraps with `t % 1.0`
(:356) and walks the polyline by arc length via `point_at_distance()` (:341-351).
`draw_glow_dot()` (:599-603) paints three concentric alpha ellipses (radii 15/10/5, alphas
42/70/210) plus a 2px white core.

**The pulsing module**: `pulse_targets` — 7 more hardcoded rects (:635-643).
`active = (idx // 6) % len(pulse_targets)` (:644) — a round-robin that advances every 6
frames; only the active one is drawn (:645-647). `pulse_rect()` (:606-610) breathes the
alpha with `int(70 + 70 * (0.5 + 0.5 * math.sin(phase)))` (:608) and draws three nested
rounded rects at grow offsets 0/4/8.

### `premium_finish(base)` — `scripts/render_animated_diagram.py:557-596` (applied once, before animation)
- **Glow**: 6 hardcoded rects (:562-569) stroked at alpha 70, GaussianBlur(4), alpha-composited (:571)
- **Film grain**: 2600 random points (:576-580), tone 120-220, alpha 4-14, from a fixed-seed RNG (:575)
- **Vignette**: a 180x170 "L" mask built pixel-by-pixel from normalised distance `(dist - 0.38) * 150` clamped to 115 (:583-591), then BICUBIC-upscaled to full size (:592) and composited as an alpha layer (:593-595)

### Is it liftable?

The *technique* is liftable and is genuinely independent of everything else: it is a pure
function `(PIL.Image, frame_index, total) -> PIL.Image`. But **as written it is bound to
this one picture** — 11 path literals + 7 rect literals + 6 glow rect literals, all in
the 1210x1138 coordinate space of the hardcoded layout. Lifting it means replacing all
24 literal lists with values **derived from the canvas graph**, which is a rewrite of the
data source, not a port of the code.

Crucially for us: **the `.gif` and the `.excalidraw` share no code path.** `ex.write()`
(:663) happens after and independently of the frame loop (:660). Animation therefore does
not, and cannot, travel through the canvas interchange format. If we want animation on the
JSON Canvas wire, it has to be **our** extension (a `griot.motion` field), because Lanshu
has no precedent to copy.

## The "hand-drawn" styling — whose roughness?

**Split answer. Both, in different outputs:**

### In the `.excalidraw`: it is **Excalidraw's own** roughness.
`scripts/render_animated_diagram.py:200` sets `"roughness": 1` on every element via
`base()`. Observed: `roughness` is `1` across all 159 elements. Excalidraw's renderer
(rough.js) applies the sketchy stroke; Lanshu just sets the flag. The per-element `seed`
(:205) is what makes rough.js's jitter stable between opens.

Value `1` is Excalidraw's "artist" level (0 = architect/clean, 1 = artist, 2 = cartoonist).
It is a **constant**, not exposed in the spec — no spec field controls roughness.

`"fontFamily": 5` (:234, :276) is the other half of the hand-drawn signal. In Excalidraw's
font enum, 5 is the hand-drawn face (Excalifont). It is hardcoded, contract-checked at
:732, and unit-tested at `tests/test_render_output_checks.py:33-46`.

### In the `.png` / `.gif`: it is **Lanshu's own**, and it is a *font* choice, not a stroke effect.
PIL draws perfectly clean geometric strokes — `draw.rounded_rectangle` (:302),
`draw.line` (:314) — there is **no roughness simulation in the raster pass at all**. The
"hand-drawn" impression in the PNG comes entirely from `font_candidates(hand=True)`
(:54-72), which returns a macOS handwriting font list:
```python
"/System/Library/Fonts/Supplemental/Chalkduster.ttf",
"/System/Library/Fonts/MarkerFelt.ttc",
"/System/Library/Fonts/Noteworthy.ttc",
"/System/Library/Fonts/Supplemental/Bradley Hand Bold.ttf",
```
`hand=True` is passed at the title (:465, :467), core panel title (:487), core card titles
(:438), and each bottom-panel title (:516, :523, :537, :544).

Plus one bespoke flourish: `draw_signature()` (:402-409) fakes a pen by printing the text
three times at ±1px offsets in purple/cyan/white (:406-407) and drawing two wobbly
underline strokes through hand-picked control points (:408-409).

So: **the styling is not portable.** The `.excalidraw` half carries its hand-drawn-ness
declaratively (liftable — it is one integer). The `.png` half carries it through macOS
font paths (not liftable — see below).

## What NOT to copy

### 1. The hardcoded layout itself — the defining limitation
`render_static()` is 99 lines of literal coordinates (:456-554). Every diagram this tool
can ever produce is the same picture with different words. That is a deliberate product
choice (`README.md:252-263`) and it is **the opposite of what layer 01 must do.** Do not
port `render_static()`. Port `Excal`.

### 2. macOS-only absolute font paths — OBSERVED to break on Windows
`font_candidates()` (:54-72) hardcodes 10 absolute `/System/Library/Fonts/...` and
`/Library/Fonts/...` paths. `load_font()` (:75-81) tries each and on `OSError` falls through
to `ImageFont.load_default()` (:81) — **a tiny fixed-size bitmap font that ignores the
requested size entirely.**

Observed on Windows this session, not inferred:
- Rendered PNG: the title, all card text, and every label collapse to a uniform ~8px
  bitmap face; the CJK subtitle `Codex + Claude Code 记忆资产归档流程` renders as tofu boxes.
- **4 of 7 unit tests FAIL**, all four for the same reason — `fit_text` measures against
  the default bitmap font, which is so small that text never needs wrapping, so
  `assertIn("\n", text)` fails (`tests/test_text_fitting.py:43`, `:58`, `:76`, `:101`).

The silent `except OSError: continue` at :79-80 means **there is no signal that this
happened** — the run still exits 0 and `--check` still reports `"ok": true`, because none
of the 12 checks look at typography.

### 3. "Deterministic output" is platform-dependent
`SKILL.md:19` says "Use the bundled renderer for deterministic output." The RNG seed
(:182) and frozen `UPDATED` (:17) do make the *numeric* fields reproducible. But
`fit_text()` (:157-173) writes the **measured** result into the `.excalidraw` —
`ex.text(text, ..., size, ...)` at :289 receives a `size` and a possibly-wrapped `text`
computed against whatever font the host OS resolved. **The same spec on macOS and Windows
produces different `fontSize` values and different line breaks in the `.excalidraw`.**
Determinism holds per-machine, not per-spec.

### 4. Duplicated coordinate literals between static and animated passes
The 11 animation paths (:618-630) are hand-copies of static arrow coordinates (:480, :492-494,
:503, :505, :509-510, :533-535, :541, :547). The 7 pulse rects (:635-643) are hand-copies of
panel rects (:476, :489-491, :497, :522, :543). The 6 glow rects (:562-569) are a **third**
copy. Three parallel lists of the same geometry with no shared source. Our version derives
all of it from the canvas node set.

### 5. Zero spec validation
`json.loads` at :761 and nothing else. A typo'd key (`core.card` instead of `core.cards`)
silently yields three blank cards via the padding at :484-485 — a successful-looking run
that produced a wrong diagram. Contrast our `validate()` / `assertValid()` posture in
`apps/prism-viz-engine/src/core/json-canvas.ts:136-199` ("Gate, don't coerce... collect
every violation, write nothing on failure"). **Keep ours.**

### 6. Silent truncation and silent padding
`inputs[:4]` (:478), `cards[:3]` (:518), `cards[:4]` (:525), `cards[:3]` (:545) — content
beyond the slot count **vanishes with no warning**. Padding (:474-475, :484-485, :526-527)
manufactures empty cards that render as blank boxes. Neither is reported in the `--check`
output.

### 7. Un-exercised defensive branch
`frame_diff_report()` :682:
```python
data = cropped.get_flattened_data() if hasattr(cropped, "get_flattened_data") else cropped.getdata()
```
`get_flattened_data` is not a Pillow API on any version in the declared range; the
`hasattr` guard means the branch is always false. Dead code carried as a false safeguard.

### 8. Hardcoded personal branding in the render path
`brand()` (:412-425) always paints an 8-dot mark at absolute `(955, 143)` and a signature
at `(998, 135)`; `draw_signature()` is called unconditionally from `render_static()` :471
with default `"@岚叔"`. There is no "no signature" option — an empty `signature` string
still draws the dots and the underline strokes.

### Maps cleanly onto JSON Canvas

| `x`/`y`/`width`/`height` on every element (`:190-193`) | `CanvasNodeBase` (`json-canvas.ts:27-30`) | **Exact field-name and semantic match.** Absolute pixel coords, same four names. Near-trivial mapping. |

| `frame_diff_report()` (`:667-685`) | — | The tool proving its own output actually moved. This is an I4-shaped idea (fresh evidence, not re-reasoning) and worth carrying into layer 02's animation verification. |

### Does NOT map — and why

| Lanshu | the problem |
|---|---|
| **The entire spec schema** (`assets/default-spec.json:1-138`) | Slot names (`left_panel`, `core.cards`, `decision`) are **presentation roles in one fixed picture**. JSON Canvas has `nodes[]` + `edges[]`. There is no translation because there is no graph to translate. **Do not model our layer-01 input on this file.** |
| **Edges** | Lanshu has no edge concept at all. Arrows are polylines with `startBinding = None`, `endBinding = None` (`:263-264`, observed 0/14 bound). `CanvasEdge` (`json-canvas.ts:59-67`) requires `fromNode` + `toNode`, **and `validate()` rejects an edge whose endpoints are not real nodes** (`json-canvas.ts:181-186`). Lanshu's output could never satisfy that check. Nothing to lift. |
| **`fromSide` / `toSide`** (`json-canvas.ts:58`, `:61`, `:63`) | No analogue. Lanshu's arrows carry raw absolute geometry; a "side" is meaningless without node binding. Anchor-side routing is entirely ours to build. |
| **Grouping / nesting** | `groupIds: []` on all 159 elements (`:201`, observed). `CanvasGroupNode` (`json-canvas.ts:49-54`) is a real container with `label` and `background`. Lanshu expresses grouping only as a *spec key name*. No mechanism to port. |
| **Node `type`** (`json-canvas.ts:22`, `text`/`file`/`link`/`group`) | Lanshu's `type` is a *shape* (`rectangle`, `ellipse`, `diamond`, `line`, `arrow`, `text`). Ours is a *semantic kind*. Same field name, different axis — do not let the name similarity mislead the mapping. |
| **Stable ids** | `rect-0012` (`:188`) is a positional counter. Add one shape earlier in `render_static()` and every downstream id shifts. Our `merge()` (`json-canvas.ts:202-208`) is id-keyed and assumes ids are *identities*. Incompatible id semantics. |
| **Layout** | There is none to lift. Layer 01 still needs its own layout pass (or must require positions on input) — **Lanshu contributes nothing here, and this is exactly the gap prior research assumed was filled.** |
| **Animation** (`:613-649`) | Sits entirely outside the interchange file, over rasterised frames, against 24 hardcoded coordinate literals. Cannot ride the JSON Canvas wire. If we want motion, it is a **new** `griot.motion` extension of our own design — the extension slot exists (`GriotNodeMeta`, `json-canvas.ts:82-121`) but there is no precedent here to copy into it. |
| **The `griot` extension** | Lanshu has no notion of provenance, `origin: {repo, file, line}`, `licence`, `layer`, `walkLevel`, or `decision` (`json-canvas.ts:88-120`). Everything that makes our nodes *evidence* rather than *ink* is absent. |
| **The macOS font stack** (`:54-72`) | Observed to degrade silently to a bitmap fallback on Windows, taking 4 unit tests with it. Prism is Windows-primary. Do not carry these paths. |
| **`fit_text` writing measured sizes into the output** (`:289`) | Couples the interchange file to host font metrics. Our wire must stay host-independent; text sizing belongs to layer 02. |

### The seam, drawn honestly

```
LANSHU          spec (content slots)  ──▶  render_static()  ──▶  PNG ──▶ GIF
                                              │ (hardcoded coords)
                                              └──▶ Excal ──▶ .excalidraw
                                                   (by-product of the raster pass)

PRISM (target)  generator ──▶ JSON Canvas (the wire) ──▶ canvas adapter ──▶ render
                              nodes[]+edges[], validated
```
The direction of the arrow into the canvas file is **reversed**. In Lanshu the file falls
out of the drawing; in ours the drawing falls out of the file. That is why `render_static()`
is un-portable and `Excal` is portable: `Excal` is the only part that does not care where
the coordinates came from.

### The honest summary of the lift

**Take:** the `Excal` class shape (105 lines, `:176-280`) as a model for a clean
accumulator+serializer; the determinism discipline (fixed seed, frozen timestamp, no
wall-clock); the self-proving output check (`check_outputs` + `frame_diff_report`); the
skill-packaging shape (`SKILL.md` trigger description + `agents/openai.yaml` surface
adapter + on-demand `references/`).

**Leave:** the spec schema, the layout, the animation binding, the fonts, and the premise
that this repo already solved graph→canvas. It solved *picture→canvas*, which is the easy
half. The hard half — a structured graph with real edges, laid out and serialized — is
still ours to build, and `apps/prism-viz-engine/src/core/json-canvas.ts` is already further
along that road than anything in this repository.
