## Stack, build, ship

- **Shell**: Tauri 2 (`apps/desktop/src-tauri`, `tauri.conf.json` schema `2`). `productName: "Open Science"`, `identifier: com.ai4s.workbench`, `version 0.5.2` (root `package.json` and `tauri.conf.json` agree). Window uses `titleBarStyle: "Overlay"` + `hiddenTitle` + explicit `trafficLightPosition` — the AppShell/Sidebar code paths built around `overlayTitlebar` (`AppShell.tsx:197-262`, `Sidebar.tsx:580-597`) exist specifically to keep content clear of the native macOS traffic lights under this config.
- **Rust surface**: 38 files under `apps/desktop/src-tauri/src` (not the "66" the prior survey cited — that count is only accurate at the *workspace* level: 68 `.rs` files total across `src-tauri/src` (38) + two standalone crates, `crates/osd-cli` (7 files) and `crates/osd-core` (23 files, not enumerated individually here). `osd-cli`'s own `Cargo.toml` description: *"osd — Open Science Desktop without a window: a headless server and a client for it."* — the Tauri app and a headless CLI both consume the same `osd-core` crate, so the native logic is written once and shipped two ways (windowed + headless).
- **Ships as**: Tauri bundle, `"targets": "all"`, with three externally-bundled binaries baked into `externalBin` (`tauri.conf.json:29-33`): `binaries/opencode`, `binaries/uv`, `binaries/agent-browser`, `binaries/osd`. `resources` (lines 55-70) stage nine more directories into the bundle at build time: `goal-plugin`, `browser-plugin`, `history-plugin`, `tools`, `computer` + `computer-use`, three skill packs (`skills/`, `skills-office/`, `skills-agent-browser/`, `skills-core/`), an OpenCode `profile/agent` + `profile/command` pair, `harness/`, `acp-server/`, and the built-in demo project (`examples/climate-trends/`). Windows ships via NSIS (`installMode: currentUser`, custom install hooks + English strings). macOS: `hardenedRuntime: true`, `minimumSystemVersion: "13.0"`.
- **pnpm workspace**, `packageManager: pnpm@9.4.0`, root scripts fan out to `--filter @ai4s/desktop`. `packages/` holds `sdk` (the `OpenCodeClient` wrapper AGENTS.md names as the mandatory UI→agent boundary), `shared` (cross-cutting types — `Project`, `Inspector`, etc., imported everywhere as `@ai4s/shared`), `ui`.
- **Testing**: Vitest + Testing Library. The `*.test.tsx` sibling-file convention is dense and consistent — nearly every non-trivial component in `components/session`, `components/thread`, `components/inspector` and every `routes/*Page.tsx` has one.

## Its own skills/plugin/extension system

Declared as a **filesystem convention consumed by OpenCode**, not a code-level plugin registry — the app doesn't invent its own plugin format, it surfaces OpenCode's:

- `apps/desktop/src/app/routes/SkillsPage.tsx` — a single page listing **skills and agents together** as one searchable/filterable catalog (`kind: "all" | "skill" | "agent"`, `entries` built at lines 43-70). Skills come from `useRuntimeStore((s) => s.skills)`, agents from `.agents` — both populated by `loadCatalog()` against the running OpenCode sidecar.
- Provenance is resolved from the reported filesystem path, `sourceOf()` (lines 344-361): `<built-in>` / `/builtin/` → **builtin**; `xdg-config/opencode/skills/user/` → **user**; `.opencode/` → **project**; anything else (including `~/.claude/skills`, `~/.agents/skills`) → **user**. Three source tiers, one function, exhaustive by the same "registry, not heuristic" shape as the route table.
- The page's own summary line (line 200-203) literally spells the install location: `` `${prefix}.opencode/skills/${suffix}` ``.
- Bundle-time, `tauri.conf.json` stages four separate skill trees into the shipped app as distinct resource dirs (`skills/` = `runtime/skills/external/ai4s-skills`, `skills-office/` = `anthropic-skills`, `skills-agent-browser/`, `skills-core/` = `runtime/skills/core`). `runtime/skills/core/` itself holds 14 domain-science skills as SKILL.md packs: `bibliometric-analysis`, `citation-reviewer`, `domain-check`, `figure-provenance`, `large-file`, `literature-review`, `modal-run`, `paper-to-report`, `publication-figures`, `remote-compute`, `reproducible-research`, `stats-integrity`, `traceability-review`, `computer-use`.
- Install path in-app: `InstallSkill` (`SkillsPage.tsx:269-342`) accepts a pasted SKILL.md or a free-text description; the store's `installSkill()` either installs it directly (toast) or spins up an agent session to build one (navigates to `/live/<id>` — installing a skill can itself be agent work, not just a file copy).

## UI is composed — not a flat file list

The 381-file `src/` tree resolves into a handful of composition layers, each with a clear owner:

1. **`AppShell.tsx`** (`apps/desktop/src/app/layout/AppShell.tsx:206-278`) — the literal shell: `Sidebar` + `Outlet` (routed page) inside a flex column, then four **app-wide overlays mounted unconditionally at shell level**, outside the route tree: `StatusBar` (268), `CommandPalette` (269), `JumpPalette` (270), `Toaster` (271), `SshSignInDialog` (275), `PaneDragGhost` (276). None of these is a "page" — they are global surfaces that must be reachable from anywhere, and the shell is where that "reachable from anywhere" property is enforced structurally (mount once, above the router).
2. **`Sidebar.tsx`** (1302 lines, `apps/desktop/src/components/sidebar/Sidebar.tsx`) does double duty as **two different navigation surfaces sharing one DOM slot**, switched on `location.pathname.startsWith("/settings")` (line 111): the normal rail (logo/home, New/Notebooks/Files/Runs/Skills quick nav at 660-692, Projects tree, session history) **or** the Settings section nav (back-to-app + the 11-row `SETTINGS_SECTIONS` list, 598-627) — never both. The code comment at 44-46 explains why: in Settings the sidebar *is* the only way back, so it's deliberately barred from collapsing there.
3. **`InspectorShell.tsx`** → **`FilePreviewInspector.tsx`** → 13+ leaf viewer components (see Registry Level 3 above) — a three-tier dispatch from "what pane is open" down to "which exact renderer for this byte format," entirely driven by the two typed registries (`Inspector.variant`, `PreviewKind`).
4. **`components/thread/`** (46 files, no subfolders) is the actual chat/session composition layer — `ThreadView.tsx` (70 lines, thin), `Composer.tsx`, `ToolCallRow.tsx`/`ToolGroup.tsx`, `SubagentPane.tsx`/`SubagentActivity.tsx`, `ReviewerCard.tsx`, `ModelPicker.tsx` (667 lines — the single largest file here), `ArtifactCard.tsx`/`InlineArtifact.tsx`, `WorkflowStarters.tsx`, and **`InteractionPrompt.tsx`** (273 lines) — the actual approval/permission surface. Notably, `components/approval-dialog/` and `components/tool-call-card/` are **empty directories** (scaffolding never filled in) while the real implementations (`InteractionPrompt.tsx`, `ToolCallRow.tsx`) live one level up in `thread/` — a naming/location drift worth flagging if this repo is ever used as a structural template.
5. **Small-but-load-bearing components, named explicitly because they're easy to skip in a file-count sweep**:
   - `CommandPalette.tsx` (119 lines) — a 7-entry `Action[]` literal array (lines 72-80) is the entire ⌘K surface. It imports `WORKFLOW_STARTERS` from `thread/WorkflowStarters.tsx` (line 19, 29) specifically so the palette's "Analyze"/"Audit" entries and the empty-session starter cards never drift out of sync — one prompt source, two entry points.
   - `JumpPalette.tsx` (205 lines) — ⌘J, explicitly commented as ported from **Orca** (line 14: *"⌘J on macOS; Ctrl+Shift+J elsewhere, as in Orca"*; line 31: *"Orca's worktree jump palette (MIT), in this app's Project → Screens → panes shape"*). `SECTIONS: JumpSection[] = ["actions", "projects", "screens", "panes", "sessions"]` (line 22) is a fifth small typed registry, one filterable list across every "place you can go."
   - `sections.ts` (55 lines total) — already covered above, but worth repeating: the entire settings nav + route-guard system is one 15-line array literal.
   - `InteractionPrompt.tsx` — the whole "agent asks a question / agent asks for permission" surface (CLAUDE.md's mandatory approval gate) is ~270 lines rendered inline above the composer, not a modal — the agent literally cannot proceed past a blocking tool call until this renders and the user answers (docstring at lines 7-11 says so directly: *"Without this, the agent's question/permission tool sits forever and the session looks stuck."*).
