## Isometric projection — the actual maths

### The constants — `config.ts:17-25`

    export const UNPROJECTED_TILE_SIZE = 100;                    // config.ts:17
    export const TILE_PROJECTION_MULTIPLIERS: Size = {           // config.ts:18-21
      width: 1.415,
      height: 0.819
    };
    export const PROJECTED_TILE_SIZE = {                         // config.ts:22-25
      width:  UNPROJECTED_TILE_SIZE * TILE_PROJECTION_MULTIPLIERS.width,   // 141.5
      height: UNPROJECTED_TILE_SIZE * TILE_PROJECTION_MULTIPLIERS.height   //  81.9
    };

Those two magic numbers are **true isometric**, not the 2:1 pixel-art dimetric: `1.415` is approximately `sqrt(2)` (the diagonal of a unit square rotated 45 degrees) and `0.819` is approximately `sqrt(2)/sqrt(3) = 0.8165` (the vertical foreshortening at the isometric camera angle, `arccos(1/sqrt(3)) = 54.74 degrees`). The ratio `0.819 / 1.415 = 0.5788`, against `1/sqrt(3) = 0.5774`. So it is a genuine 30-degree isometric projection.

### Tile -> screen — `utils/renderer.ts:85-110` (`getTilePosition`)

    const halfW = PROJECTED_TILE_SIZE.width / 2;    // renderer.ts:89
    const halfH = PROJECTED_TILE_SIZE.height / 2;   // renderer.ts:90

    const position: Coords = {                       // renderer.ts:92-95
      x:   halfW * tile.x - halfW * tile.y,
      y: -(halfH * tile.x + halfH * tile.y)
    };

That is the whole transform — a 2x2 matrix, no perspective, no 3D:

    [ sx ]   [  halfW   -halfW ] [ tile.x ]
    [ sy ] = [ -halfH   -halfH ] [ tile.y ]

`renderer.ts:97-109` then offsets by a `TileOrigin` of `'TOP' | 'BOTTOM' | 'LEFT' | 'RIGHT' | 'CENTER'` (default `'CENTER'`) — these are the four **diamond vertices** of a tile, used as connector attach points.

`utils/renderer.ts:116-123` (`isoToScreen`) adds the viewport half-extent to land in screen space:

    return { x: position.x + rendererSize.width / 2, y: position.y + rendererSize.height / 2 };

### Screen -> tile (the inverse, for hit-testing) — `utils/renderer.ts:51-78` (`screenToIso`)

    const projectedTileSize = SizeUtils.multiply(PROJECTED_TILE_SIZE, zoom);   // :57
    const projectPosition = {                                                  // :61-64
      x: -rendererSize.width  * 0.5 + mouse.x - scroll.position.x,
      y: -rendererSize.height * 0.5 + mouse.y - scroll.position.y
    };
    const tile = {                                                             // :66-75
      x:  Math.floor((projectPosition.x + halfW) / projectedTileSize.width  - projectPosition.y / projectedTileSize.height),
      y: -Math.floor((projectPosition.y + halfH) / projectedTileSize.height + projectPosition.x / projectedTileSize.width)
    };

Note `zoom` is folded into the **inverse only** (`:57`); the forward transform at `:85-110` is zoom-free because zoom is applied as a GSAP/CSS `scale` on the layer container (`SceneLayer.tsx:36`). The two halves of the same transform therefore live in different coordinate regimes and are kept in sync by hand.

**Verified absence:** `grep -rn "rotateX|rotateZ|matrix3d|skew" components/ styles/` returns **zero matches**. No CSS 3D, no WebGL, no canvas — DOM elements positioned by arithmetic. Architecturally simple, and the one genuinely attractive property of this codebase.

### Connector routing — `utils/pathfinder.ts`

Edges are not straight lines. `packages/fossflow-lib/package.json:40` depends on `pathfinding@^0.4.18` (A* on a grid); `config.ts:56-58` defines the search window:

    // The boundaries of the search area for the pathfinder algorithm
    // is the grid that encompasses the two nodes + the offset below.
    export const CONNECTOR_SEARCH_OFFSET = { x: 1, y: 1 };

Connectors are **grid-routed orthogonal paths through tile space**, not bezier curves. A real capability our xyflow canvas does not have.

`schemas/views.ts:7-22` — a **view** places items on tiles, and a model may hold **many views over the same items**:

### Side-by-side with JSON Canvas (`apps/prism-viz-engine/src/core/json-canvas.ts`)

| Concern | JSON Canvas (`json-canvas.ts`) | FossFLOW | Converts? |
|---|---|---|---|
| Node identity | `CanvasNodeBase` `:24` | `modelItemSchema` `schemas/modelItems.ts:4` | YES — both `id` + string fields |
| **Position** | **on the node** — `x,y` on `CanvasNodeBase:24` | **on the VIEW** — `viewItem.tile` `views.ts:9` | PARTIAL — structural split, requires a join |
| **Size** | **`width`/`height` on the node** `:24` | **does not exist** — every item occupies exactly one tile | **NO — information is DESTROYED** |
| Coordinate space | **continuous pixels** | **integer tile indices** `common.ts:3-6` | **NO — lossy both ways** |
| Node kinds | `text`, `file`, `link`, `group` (`:22`) | icon-ref only (`icon: id`) `modelItems.ts:8`; `group` ~ `rectangle`, `text` ~ `textBox` — **separate arrays, not node types** | PARTIAL |
| Edge endpoints | `fromNode`/`toNode` `:59-67` | `anchors[]` — an ordered **N-anchor** list, `connector.ts:24` | PARTIAL — reverse takes first+last, as `exportOptions.ts:56-59` itself does |
| **Edge side hints** | **`fromSide`/`toSide`** — `top`/`right`/`bottom`/`left` (`:58, :62`) | **`TileOrigin`** — `TOP`/`RIGHT`/`BOTTOM`/`LEFT`/`CENTER` (`utils/renderer.ts:97-109`) | **FALSE FRIEND — same names, different geometry** |
| Multiple layouts per graph | NO — one canvas = one layout | YES — `views: []`, N layouts per model (`model.ts:17`) | FossFLOW is strictly richer here |

**Verdict on conversion: NOT clean in either direction.**

- **Ours -> theirs** is *lossy*: every node's `width`/`height` is discarded (FossFLOW has no node size), and continuous `x,y` must be quantised onto an integer tile lattice — which collides overlapping nodes and destroys any layout our force or dagre passes produced.
- **Theirs -> ours** requires *inventing* data: a join across `model.items` x `view.items` to recombine identity with position, plus a fabricated pixel scale and fabricated `width`/`height` for every node.
- The `fromSide`/`toSide` correspondence is a **false friend**: the four words match, the geometry does not. A JSON Canvas `right` is the midpoint of a rectangle's right edge; a FossFLOW `RIGHT` is a **vertex of a rotated diamond**.

The model/view split is a genuinely good idea our JSON Canvas core lacks. But it means FossFLOW is **not a JSON-Canvas-shaped renderer with a different paint style** — it is a different data model that happens to also draw boxes and lines.

The monorepo cleanly separates the two (`package.json:6-8`, workspaces `packages/*`):

## What NOT to copy

Observed facts about this codebase, recorded for our own engine's benefit:

1. **The dead-namespace provenance chain.** The published package points its `repository` field at a URL that 404s under a **recycled username** (`packages/fossflow-lib/package.json:8-11`). Our packages' `repository` fields must resolve, and we should not depend on a package whose source cannot be reached.
2. **`react-router-dom` as a dependency of a rendering library** (`package.json:44`). A component library that pulls a router forces routing decisions on every host app that embeds it.
3. **The forward/inverse transform split across two coordinate regimes.** Forward (`renderer.ts:85-110`) is zoom-free because zoom lives in a GSAP CSS `scale` (`SceneLayer.tsx:36`); the inverse (`renderer.ts:51-78`) must re-multiply zoom by hand at `:57`. Two representations of one transform, kept in agreement manually.
4. **Unlabelled magic constants.** `width: 1.415, height: 0.819` (`config.ts:19-20`) are `sqrt(2)` and `sqrt(2)/sqrt(3)` with no comment saying so. Ours should name the derivation.
5. **Self-flagged organisational debt.** `config.ts:16`, verbatim: `// TODO: This file could do with better organisation and convention for easier reading.` The file then defines the projection constants, all entity defaults, colours, fonts, and pathfinder tuning in one bag.
6. **Naming that outlived the rename.** Exports are still `isoflow-export-*.json` (`exportOptions.ts:7`), the primary component is still `Isoflow` (`Isoflow.tsx:82`), the internal package is `fossflow-lib` while the npm name is `fossflow`, and the root docs are `ISOFLOW_ENCYCLOPEDIA.md` / `ISOFLOW_TODO.md`. Three names for one thing. (Compare our I6: a rename should leave a **resolving alias**, not a half-applied rename.)
7. **Example fixture data reachable from the production export path.** `exportOptions.ts:4` imports `icons as availableIcons` from `../examples/initialData`.
8. **PNG-only raster export** (`exportOptions.ts:178-185`) via `dom-to-image`. No SVG. For a diagramming tool whose output is meant for documents, vector export is absent.

## FIT VERDICT

### For `prism-viz-engine` layer 02, as a third canvas: **NO. Weak match — do not adopt.**

Plainly, because a weak match must read as weak: **FossFLOW does not belong in the engine.** The audit's routing to family **"C · infra -> Griot Hub"** was **correct**, and this deeper read strengthens it rather than overturning it.

Reasons, in order of weight:

1. **The scene model is not ours, and does not convert cleanly.** This is the disqualifier on its own, independent of staleness or provenance. Our layer 02 canvases (xyflow, react-force-graph) share one contract: **nodes with continuous `x,y,width,height` and 2-endpoint edges** (`src/core/json-canvas.ts:24, :59`). FossFLOW is **integer tile indices with no node size** (`schemas/common.ts:3-6`, `schemas/views.ts:9`) with **identity split from position across `items`/`views`** (`schemas/model.ts:15-17`). Round-tripping destroys `width`/`height` and quantises layout. A third canvas that cannot render the same document as the other two is not a third canvas — it is a second product.
2. **The lattice is the point, and the lattice is not ours.** Isometric value comes *from* tile snapping, orthogonal A* connector routing (`pathfinding`, `config.ts:56-58`), and an isometric icon set (`@isoflow/isopacks`). Strip those to fit our model and nothing distinctive is left; keep them and we are running a separate pipeline behind one seam.
3. **Provenance is broken.** Upstream `stan-smith/*` is 404; the username is **recycled by an account created 2026-05-14 with 0 repos**; the npm package's `repository` field points into that void; `isoflow` on npm is ~1.9 years unpublished; our local copy is a **shallow, 1-commit clone of a fork of a fork**. A core rendering layer is the last place to accept an unresolvable dependency chain.
4. **It imports a second UI framework.** MUI 5 + Emotion + GSAP + Paper + Quill + a router (`package.json:28-49`), themed through MUI's `ThemeProvider` (`Isoflow.tsx:84`), which does not speak Griotwave tokens.

**What genuinely argues for it — recorded so the case is not strawmanned:** embeddability is real and better than expected (a published component library, a first-class read-only mode, peer-dep React, instance-scoped stores, and a deliberate `window`-free bundle at `standaloneExports.ts:1-2`); the projection maths is **~25 lines of clean 2x2 arithmetic** with no WebGL and no CSS 3D (`utils/renderer.ts:51-123`); the model/view split (N layouts per model, `model.ts:17`) is better than JSON Canvas's single-layout assumption; and the ecosystem has a live continuation at `Abrar74774/FossFLOW` (2026-08-24). None of that outweighs a scene model that cannot hold our document.

### For **Griot Hub**: **YES, conditionally — and this is where it belongs.**

Griot Hub's job is infrastructure and service topology, which is *exactly* the shape FossFLOW's tile lattice is built for: fixed-size service icons on a grid, orthogonal routed links, zones as rectangles (`schemas/rectangle.ts:4-9`). The model/view split maps naturally onto "one infrastructure inventory, several diagrams of it." The embed path is a normal React mount — `editorMode="EXPLORABLE_READONLY"` for viewing, `EDITABLE` for authoring — and the compact-JSON format (`exportOptions.ts:40-159, 169-176`) is purpose-built for LLM generation, which suits an agent drawing an infra diagram from a service inventory.

Conditions, if Griot Hub proceeds:

- Track **`Abrar74774/FossFLOW`** (MIT, branch `master`, active 2026-08-24) — **not** this clone, and **not** npm `fossflow@1.0.5` whose source repo is gone. Because the continuation is a **re-upload with a severed fork graph**, expect to **vendor rather than merge**.
- Treat it as **vendored third-party code from an orphaned lineage**: pin it, vendor it, own it. There is no maintainer to escalate to.
- Budget for the MUI/Emotion footprint inside Griot Hub specifically, where a second UI framework is a far cheaper decision than inside a rendering engine.

### Bottom line

Two different questions, two different answers. **Layer 02 of `prism-viz-engine`: no** — the scene model is fundamentally different, not merely differently styled, and the provenance chain is broken. **Griot Hub: yes, with eyes open.** The audit routed this correctly the first time; the new information (recycled namespace, dead upstream, fork-of-a-fork clone, live continuation elsewhere) should be written back into the harvest table, which currently records neither the staleness nor the provenance break.
